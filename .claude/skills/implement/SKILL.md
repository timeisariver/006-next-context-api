仕様書 `$ARGUMENTS` を実装する。

## 1. 準備

1. 仕様書、`CLAUDE.md`、`docs/architecture.md` を読む。
2. 仕様書に、実装方針が変わるほど曖昧な点や矛盾があれば、**実装を始める前に**ユーザーに質問する。推測で埋めない。
3. `git status --short` が空であることを確認する。未コミットの変更がこの仕様書だけなら、`docs: <機能名>の仕様書を追加` のようにコミットしてから進む。それ以外の変更があれば止めてユーザーに確認する。
4. main にいる場合は `feature/<仕様書のファイル名>` ブランチを作って切り替える。

## 2. タスク分割

新しいコードの置き場所は `feature-sliced-design` スキルの判断基準で決める（迷ったら `_pages` に置き、今まさに複数箇所で使うまでは `entities`・`shared` に切り出さない）。そのうえで、FSD のスライス単位で、**変更するファイルが重ならないように**タスクを分ける。

- 下のレイヤー（`shared`、`entities`）の変更は第 1 段階、それを使う `_pages` のスライスは第 2 段階にする。同じ段階のタスクは並列に実行する。
- `_app/layouts` など、複数のタスクが触りそうな共有ファイルは 1 つのタスクにまとめる。
- 変更が 1 スライスで済むなど小さい場合は、無理に分けずに 1 タスクにする。

各タスクについて、目的、担当するファイル・ディレクトリ、満たすべき仕様の要件、前の段階で作られる公開 API を決める。
分割の結果を短くユーザーに示してから、そのまま次へ進む。

## 3. 並列実装

段階ごとに、`implementer` サブエージェントを **1 つのメッセージで同時に**起動する。

- `subagent_type: "implementer"`、`isolation: "worktree"` を指定する。
- サブエージェントは会話の文脈を持たないので、依頼文だけで作業できるように書く: 仕様書のパス、担当タスクの内容と担当範囲、満たすべき要件、使ってよい公開 API、ベースのコミット SHA（`git rev-parse HEAD`）。

全員の完了を待ち、段階ごとに統合（次の 4.）してから次の段階を起動する。

## 4. 統合

1. 各サブエージェントの結果に含まれる worktree のブランチを、作業ブランチに `git merge` する。競合したら、両方の意図を残して解決する。
2. マージしたら `git worktree remove` と `git branch -d` で worktree とブランチを片付ける。
3. `npm run typecheck`、`npm run lint`、`npm run format:check` を実行し、エラーがあれば直してコミットする。

## 5. レビュー

次の 2 つを並列に実行する。

- `fsd-reviewer` サブエージェント: 仕様書のパスを渡し、`main...HEAD` の差分をレビューさせる。
- 組み込みの `code-review` スキル（Skill ツール）: バグの検出。

確実な違反・バグは直してコミットし、もう一度 4. のチェックを通す。判断が分かれる指摘は直さずにユーザーに報告する。

## 6. 報告

ユーザーに次を伝える。

- 実装した内容（仕様の要件ごとに対応状況）
- レビューで直したこと、直さずに残した指摘
- サブエージェントが自分で判断した点
- ユーザーが確認すべきこと（`npm run dev` で見てほしい画面など）と、問題なければ `/pr` で PR を作れること
