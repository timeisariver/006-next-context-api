プラン `$ARGUMENTS` を実装する。

## 1. 準備

1. プランと、プランに書かれた仕様書、`CLAUDE.md`、`docs/architecture.md` を読む。プランが見つからなければ、`/plan <仕様書のパス>` で先に作るようユーザーに伝えて**ここで止める**。
2. プランや仕様書に、実装方針が変わるほど曖昧な点や矛盾があれば、**実装を始める前に**ユーザーに質問する。推測で埋めない。
3. `git status --short` が空であることを確認する。未コミットの変更がこの仕様書とプランだけなら、`📝 docs: <機能名>の仕様書と実装プランを追加` のようにコミットしてから進む。それ以外の変更があれば止めてユーザーに確認する。
4. 現在のブランチがプランの「ブランチ」と違えば、止めてユーザーに確認する。
5. `git fetch origin` する（レビューの比較元は `origin/main`）。

## 2. タスクの確認

プランの「タスク」をそのまま使う。各タスクの目的、担当範囲、満たすべき要件、公開 API はプランに書かれている。

- プランを書いた後にコードが変わり、担当範囲のファイルがない・公開 API が既にあるなど、プランどおりに進められない場合は、止めてユーザーに確認する。
- 同じ段階のタスクで担当範囲が重なっていたら、止めてユーザーに確認する（並列に実装すると競合するため）。

## 3. 並列実装

段階ごとに、`implementer` サブエージェントを **1 つのメッセージで同時に**起動する。

- `subagent_type: "implementer"`、`isolation: "worktree"` を指定する。
- サブエージェントは会話の文脈を持たないので、依頼文だけで作業できるように書く: 仕様書とプランのパス、担当タスクの番号・内容と担当範囲、満たすべき要件、使ってよい公開 API、ベースのコミット SHA（`git rev-parse HEAD`）。
- 担当範囲に応じて、先に読むルールも依頼文に書く。UI コンポーネント・SCSS を含むなら `.claude/rules/ui-component.md`、`src/shared/api/` を含むなら `.claude/rules/api-types.md`。新しいファイルを作るだけだと、ルールが自動で読み込まれないことがあるため。

全員の完了を待ち、段階ごとに統合（次の 4.）してから次の段階を起動する。

## 4. 統合

1. 各サブエージェントの結果に含まれる worktree のブランチを、作業ブランチに `git merge` する。競合したら、両方の意図を残して解決する。
2. マージしたら `git worktree remove` と `git branch -d` で worktree とブランチを片付ける。
3. `npm run typecheck`、`npm run lint`、`npm run format:check` を実行し、エラーがあれば直してコミットする。

## 5. レビュー

次の 2 つを並列に実行する。

- `fsd-reviewer` サブエージェント: 仕様書のパスを渡し、`origin/main...HEAD` の差分をレビューさせる。
- 組み込みの `code-review` スキル（Skill ツール）: バグの検出。

確実な違反・バグは直してコミットし、もう一度 4. のチェックを通す。判断が分かれる指摘は直さずにユーザーに報告する。

## 6. 報告

ユーザーに次を伝える。

- 実装した内容（仕様の要件ごとに対応状況）と、プランから外れたことがあればその理由
- レビューで直したこと、直さずに残した指摘
- サブエージェントが自分で判断した点
- ユーザーが確認すべきこと（`npm run dev` で見てほしい画面、コードで特に見てほしい箇所など）と、問題なければ `/pr` で PR を作れること
