### 2. プルダウンを共通化し、見た目を揃える（PR #2）

レビューで「プルダウンはプロジェクト全体で同じ見た目であるべきで、それなら共通化できる」と指摘された。今は 4 か所のプルダウンが、それぞれ別の CSS で少しずつ違う見た目になっている。標準の `<select>` では開いたときの選択肢の一覧に CSS を当てられないため、一覧も含めてデザインできる自作のプルダウンにする。

#### 選択肢の定義

- [ ] タスクのステータスの選択肢（未完了・完了・アーカイブ）を `entities/task` の一か所で定義する。今は `TaskRow`・`TaskDetailForm`・`TaskCreateModal` の 3 か所に同じ定義がある
- [ ] 「プロジェクト一覧に今のプロジェクトがなければ選択肢に足す」処理を `entities/task` の一か所にまとめ、`TaskRow` と `TaskDetailForm` で使う

#### 自作のプルダウン部品

- [ ] 標準の `<select>` を使わないプルダウン部品（`Select`）を `shared/ui` に作る
- [ ] 閉じているときは、選んでいる項目の名前と下向き矢印のアイコン（Lucide の `ChevronDown`）を表示する
- [ ] 何も選んでいないときは、プレースホルダー（例:「プロジェクトを選択してください」）を薄い文字色（`var(--color-text-muted)`）で表示する
- [ ] クリックすると選択肢の一覧が下に開き、項目をクリックするとその項目が選ばれて一覧が閉じる
- [ ] 一覧の外をクリックすると、何も選ばずに一覧が閉じる
- [ ] 選んでいる項目は、一覧の中で分かるように表示する（文字色 `var(--color-primary)`）。マウスを乗せた項目とキーボードで移動中の項目は背景色（`var(--color-primary-bg)`）で示す
- [ ] 一覧は、表のセルやモーダルの中でも周りの要素に隠れずに表示される
- [ ] 選択肢が多いときは、一覧の中をスクロールできる
- [ ] 無効（`disabled`）のときはクリックしても開かず、薄く表示する
- [ ] エラーのとき（`aria-invalid`）は枠線を `var(--color-danger)` にする

#### キーボード操作と読み上げ

- [ ] Tab でフォーカスでき、フォーカスしていることが見て分かる
- [ ] フォーカスした状態で Enter・Space・下キーを押すと一覧が開く
- [ ] 一覧が開いているとき、上下キーで項目を移動し、Enter で選んで閉じる。Esc で何も選ばずに閉じる。閉じたあとはプルダウンにフォーカスが戻る
- [ ] スクリーンリーダー向けに、プルダウン・一覧・項目の役割（`combobox`・`listbox`・`option`）と、開閉の状態・選ばれている項目を伝える
- [ ] `<label>` と結び付けられ、ラベルをクリックするとプルダウンにフォーカスが移る。ラベルがない場所（タスクの表）では `aria-label` で名前を付けられる
- [ ] `npm run lint`（jsx-a11y）がエラーにならない

#### 見た目

- [ ] 見た目は 1 種類に揃え、今のタスク追加モーダルのプルダウンを基準にする（枠線 1px `var(--color-border)`、角丸 8px、影 `var(--shadow-card)`、背景 `var(--color-surface)`、矢印は右端）
- [ ] 狭い場所で使うため、大きさだけ「標準」と「小」を選べるようにする。「小」は文字・余白・矢印を小さくし、色・枠線・角丸・影の考え方は「標準」と同じにする
- [ ] 開いた一覧は、プルダウンと同じ幅以上で、背景 `var(--color-surface)`、枠線 `var(--color-border)`、角丸 8px、影付きにする
- [ ] 色・影は `src/_app/styles/globals.scss` の CSS 変数だけを使う

#### 使う場所

- [ ] 次のプルダウンをすべてこの部品に置き換える
  - タスクの表（ダッシュボード・`/tasks`）のプロジェクト・ステータス（「小」）
  - タスク詳細（`/tasks/<id>`）のプロジェクト・ステータス（「標準」）
  - タスク追加モーダルのプロジェクト・ステータス（「標準」）
  - `/tasks` の表示件数（`LimitSelect`、「小」）
- [ ] タスクの表のプロジェクト・ステータスが、変更前と同じ選択肢で表示され、選ぶと保存される。保存中は無効になる
- [ ] タスク詳細とタスク追加モーダルのプロジェクト・ステータスが、変更前と同じ選択肢・初期値で表示される
- [ ] タスク追加モーダルを開くと、プロジェクトのプルダウンにフォーカスが移る。プロジェクトを選ばずに「作成」を押すと、エラーが表示されて枠線が赤くなる
- [ ] `/tasks` の表示件数が、変更前と同じ選択肢で表示され、選ぶと表示件数が変わる
- [ ] プロジェクト一覧の取得前や取得失敗時も、タスクが今属しているプロジェクトが選択肢に残る（表・タスク詳細）

### 3. 進捗サマリーの取得を async/await で書く（PR #4）

- [ ] ダッシュボードの進捗サマリー（`Summary`）の統計の取得を、`.then` / `.catch` / `.finally` ではなく async/await と try/catch/finally で書く
- [ ] 読み込み中は「読み込み中…」、取得に失敗したら「進捗の取得に失敗しました」、データがなければ「データがありません」と表示される

### 4. 日付まわりの関数を一か所にまとめる（PR #8）

- [ ] 日付の表示形式の変換（`YYYY/MM/DD`・`YYYY-MM-DD`・`M / DD`）、期限までの残り日数の文言（「あと N 日」「今日まで」「N 日超過」）、今日の日付（`YYYY-MM-DD`）を求める処理を `shared/lib/date.ts` にまとめ、各コンポーネントはそれを使う
- [ ] `entities/task/lib/date.ts` の関数（`toDateString`・`toDisplay`）も `shared/lib/date.ts` に移し、`entities/task/lib/date.ts` はなくす
- [ ] 変換のやり方は変えない。`dayjs` を使っている箇所は `dayjs` のまま、文字列の先頭を切り出している箇所（タイムゾーン変換をしない）は切り出しのままにする
- [ ] 次の表示が変更前と同じになる
  - サイドバー・ダッシュボードの最近のプロジェクト・`/projects` のカードの期限日（`YYYY/MM/DD`）
  - `/projects/<slug>` の残り日数と期限日
  - 進捗サマリーの棒グラフのラベル（`M / DD`）と期間（`YYYY-MM-DD ~ YYYY-MM-DD`）
  - タスクの表の期限日、タスク詳細の締切日・作成日時・更新日時
  - タスク追加モーダルを開いたときの締切日の初期値（今日）

### 5. タスク追加モーダルを分割する（PR #9）

- [ ] タスク追加モーダルを次の 3 つに分ける
  - 開閉状態を管理する hooks（`shared/lib` に置く）
  - モーダルの輪郭とオーバーレイ（`<dialog>` の表示、閉じるボタン、背景クリック・Esc で閉じる、開いている間の背面スクロール禁止）を扱うコンポーネント（`shared/ui/Modal` に置く）。タスク追加以外のモーダルでも使える
  - タスク追加のフォーム（`useProjects()` を使うタスク追加専用のものなので、`_app/layouts` に残す）
- [ ] ヘッダーは開閉状態の hooks を使ってモーダルを開閉する
- [ ] ヘッダーの「タスクを追加」ボタンでモーダルが開く
- [ ] 閉じるボタン・キャンセルボタン・背景のクリック・Esc でモーダルが閉じる
- [ ] モーダルを開いている間は背面のページがスクロールしない
- [ ] 開くと最初の入力欄（プロジェクト）にフォーカスが移る
- [ ] 閉じて開き直すと、入力内容が初期値に戻る
- [ ] 必須項目（プロジェクト・タスク・締切日）が空のまま「作成」を押すと、各項目の下にエラーが表示される。すべて入力して「作成」を押すとモーダルが閉じる（API には送らない）

## 対象外

- プルダウン以外の見た目・文言・動作の変更（バグを見つけても、この仕様書では直さない）
- プルダウンの検索（文字を入力して選択肢を絞り込む）・複数選択
- 日付の入力欄（`type="date"`）やテキスト入力欄の見た目を揃えること
- タスク追加モーダルからの API 送信（タスクの作成）の実装
- 進捗サマリーの期間の切り替え、ヘッダーの検索・ヘルプ・通知の実装
- `/tasks` と `/projects` の `Pagination` の共通化など、レビューで指摘されていない重複の整理
- 新しいモーダル（削除の確認など）の追加
- テストフレームワークの導入

## 使う API・データ

API の呼び方は変えない。

## デザイン・補足

- レビューコメント: [PR #2](https://github.com/timeisariver/006-next-context-api/pull/2)、[PR #4](https://github.com/timeisariver/006-next-context-api/pull/4)、[PR #8](https://github.com/timeisariver/006-next-context-api/pull/8)、[PR #9](https://github.com/timeisariver/006-next-context-api/pull/9)
- PR #9 の指摘の全文（モーダルの分け方）:
  > モーダルの実装などでは、1. 表示・非表示の状態を管理するための hooks、2. モーダルの輪郭やオーバーレイを制御するコンポーネント、3. 実際のフォームを実装したコンポーネントの 3 つに分割して実装することが多いです。このようにコンポーネントをわけておくと、3 だけを実装すれば他の 1. 2. の挙動は一貫したものにできる、1、2 のコンポーネントは動作保証済みで使い回せる、といった視点もあるので再利用観点や coding agent が修正する範囲を限定する視点を以て実装できるとさらによくなりそうです。
- 進捗サマリーの async/await は、`ProjectsProvider`（`src/entities/project/model/ProjectsContext.tsx`）の `init()` の書き方に揃えられる。
- `.then(` を使っているのは現在 `Summary.tsx` だけ。
- 置き場所の考え方（FSD）:
  - 日付の整形や開閉状態の hooks は業務に依存しないため `shared` に置く。UI を持たない関数・hooks は `lib` セグメントに置く（`shared/lib` は新しく作る。`shared` はスライスを持たないので、`shared/lib/index.ts` を Public API にする）。
  - ステータスの選択肢と、プロジェクトの選択肢を補う処理はタスクの業務ルールなので `entities/task` に置く。
  - `dayjs` に揃えないのは、日時がブラウザのタイムゾーンに変換され、日本以外の環境で表示が 1 日ずれることがあるため。
- `shared/lib` を足すときは、`docs/architecture.md` のディレクトリ構成とセグメントの説明も合わせて更新する。
- 見た目が変わらないこと（プルダウン以外）と、プルダウンが揃ったことは、変更前後のスクリーンショットで確認する。プルダウンは一覧を開いた状態も撮る。
- プルダウンの Figma のデザインはない。基準はタスク追加モーダルのプルダウン（`src/_app/layouts/TaskCreateModal.module.scss` の `.control`・`.select`・`.chevron`）。
- 自作プルダウンの参考（レビューのサンプル）。`div`・`ul`・`li` で組んでいる。ただしサンプルにはキーボード操作と ARIA の役割がないため、構造だけを参考にし、上の「キーボード操作と読み上げ」の要件を満たすようにする。
  ```html
  <div class="container">
    <div class="valueContainer">
      <p class="value">プログラムを選択してください</p>
      <div class="iconContainer"><!-- ChevronDown --></div>
    </div>
    <div class="pullDownContainer pullDownShow">
      <ul class="pullDown">
        <li class="option" value="…">プログラミング</li>
        <li class="option" value="…">英語</li>
      </ul>
    </div>
  </div>
  ```
- キーボード操作と ARIA は、WAI-ARIA Authoring Practices の「Select-Only Combobox」のパターンに沿う。

### 進め方とコミット

PR は分けず、このブランチで 5 件すべてを対応する。コミットはレビューコメントごとに 1 つに分け、どのコミットがどの指摘への対応か分かるようにする。
